## 규모의 문제

지원자 한 명의 제출물을 꼼꼼히 리뷰하는 데 약 30분. 소스코드, 문서, 프롬프트, git 이력, 테스트 커버리지, 데이터 설계까지. 366명이면 184시간. 한 사람이 주 40시간 일해도 한 달이 걸립니다.

하지만 시간이 진짜 문제가 아닙니다. 수동 리뷰에는 세 가지 구조적 한계가 있습니다:

**일관성.** 리뷰어 A는 코드 품질에 관대하고, B는 엄격합니다. C는 아침에는 날카롭고 오후에는 느슨합니다. 200번째 제출물과 20번째 제출물이 같은 기준으로 평가될 수 없습니다. 366명이면 이 편향이 노이즈로 쌓입니다.

**부분 인정.** 이것이 미묘한 문제입니다. Docker 빌드가 실패한 지원자는 기능 테스트 점수가 0점이지만, 소스코드를 보면 설계 사고가 탁월할 수 있습니다. 반대로 앱은 완벽하게 돌아가지만, 코드를 보면 AI가 생성한 스캐폴드를 얇게 이해한 채 제출한 경우도 있습니다. 사람이 이해한 것과 AI가 생산한 것을 어떻게 구분할까요? 이진 판정은 이 신호를 파괴합니다.

**속도.** 채용 일정은 기다려주지 않습니다. 평가, 랭킹, 면접 대상 선별, 면접 가이드 생성, 일정 조율까지 모두 몇 주 안에 끝내야 했습니다.

자동화되고, 일관되고, 다차원적 채점이 가능한 시스템이 필요했습니다. 그래서 만들었습니다.

## AI 에이전트, 직접 만들지 않은 이유

첫 번째 본능은 처음부터 직접 만드는 것이었습니다. Docker 오케스트레이션을 위한 Python 스크립트, 코드 리뷰를 위한 LLM API 호출, 결과 파싱을 위한 커스텀 파서. 하지만 범위가 만만치 않았습니다. 한 명의 평가에 필요한 동작만 나열해도: git clone, 커밋 마감 체크, 보안 스캔, 형식 검증, 8개 영역 코드 분석 채점, Docker 빌드 및 기동, 헬스체크, curl로 25개 TC 실행, 점수 산출, 리포트 생성, 외부 시스템 업데이트, 정리. 이것을 366명에 대해 반복합니다.

이 모든 것을 기존 소프트웨어로 만들면 그 자체로 하나의 프로젝트입니다. 자체 버그, 테스트, 배포, 유지보수까지 따라옵니다. 몇 달이 아니라 몇 주가 주어진 상황이었습니다.

핵심 인사이트: **에이전트를 만들 필요가 없었습니다. 에이전트를 위한 지침서를 만들면 됐습니다.**

최신 AI 에이전트는 이미 코드를 읽고, 쉘 명령을 실행하고, Docker 컨테이너를 빌드하고, 외부 API를 호출하고, 파일 시스템을 관리할 수 있습니다. 스스로 하지 못하는 건 366명에 걸쳐 특정 평가 절차를 일관되게 따르는 것뿐입니다.

그래서 평가 소프트웨어 대신 평가 지침서를 작성했습니다. 채점 기준, 테스트 케이스 정의, 실행 절차를 버전 관리되는 마크다운 파일로. 에이전트가 이 파일을 읽고 실행합니다. 배점을 바꾸고 싶으면? 마크다운을 수정하고 push. 테스트 케이스를 추가하고 싶으면? 시나리오 파일을 업데이트. 지침서가 곧 프로그램입니다.

이것을 "Markdown as Code"라고 부르기 시작했습니다. 채점 루브릭, TC 정의, 실행 흐름이 사람이 읽을 수 있고, 버전 관리되고, diff가 되는 텍스트 파일에 담겨 있습니다. 채점 모델을 바꿀 때(17번 바꿨습니다), git diff로 정확히 무엇이 바뀌었는지 볼 수 있었습니다. 뭔가 잘못 채점되면 루브릭의 특정 줄까지 추적할 수 있었습니다.

역할 분리가 깔끔했습니다: 에이전트는 능력(코드 읽기, Docker, 쉘, API 호출)을 제공하고, 우리는 지침(무엇을 평가하고, 어떻게 채점하고, 어떤 형식으로 출력할지)을 제공합니다. 평가 기준의 반복 속도가 소프트웨어 배포가 아니라 문서 편집 속도가 됩니다.

## 7단계 파이프라인

각 지원자의 제출물은 7단계를 거칩니다. 모든 단계는 구조화된 JSON을 생산하고(어떤 단계든 독립적으로 재실행 가능), 외부 상태를 업데이트합니다(대시보드와 모니터링용).

**Init.** 지원자의 저장소를 clone합니다. 커밋 타임스탬프를 제출 마감과 대조합니다. 마감 이전 마지막 유효 커밋으로 checkout합니다.

**Stage 0 — 보안 스캔.** 지원자가 제출한 임의의 코드를 Docker 컨테이너에서 실행하게 됩니다. 무엇보다 먼저 쉘 인젝션, 비인가 네트워크 요청, 임베디드 시크릿을 스캔합니다. 통과 아니면 탈락의 이진 게이트입니다.

**Stage 1 — 형식 검증.** README가 있는가? 소스 디렉토리가 있는가? 빌드 설정이 있는가? 산출물을 정리하지 못하는 것도 신호이긴 하지만, 여기서는 점수가 아닌 게이트입니다.

**Stage 2 — AI 품질 평가 (~120점).** AI가 지원자의 코드를 읽는 단계입니다. 에이전트가 8개 영역을 평가합니다: 프롬프트 품질, 에이전트 지침, 요구사항 도출, 데이터 설계, 코드 품질, 테스트 품질, git 이력, 추가 구현. 모든 점수에는 구체적 근거(파일 경로, 라인 번호, 코드 인용)가 필요합니다. 감에 의한 채점은 없습니다.

**Stage 3 — Docker 기능 테스트 (100점).** 머신이 코드를 실행하는 단계입니다. Docker 컨테이너를 빌드하고, 앱을 기동하고, 헬스체크를 기다린 뒤, 8개 카테고리 25개 TC를 실행합니다. 동시성 테스트는 통계적 신뢰도를 위해 2-3회 반복합니다. 각 TC는 래더 채점(pass/fail이 아닌 "시도 없음"부터 "탁월"까지의 스펙트럼)을 사용합니다.

이중 구조는 의도적입니다. Stage 2는 묻습니다: 지원자가 자신이 만든 것을 *이해하고 있는가?* Stage 3는 묻습니다: 만든 것이 실제로 *동작하는가?* 둘 다 필요합니다. 설계 문서는 훌륭하지만 코드가 망가진 지원자도 있고, 코드는 돌아가지만 왜 돌아가는지 모르는 지원자도 있습니다. 머신은 두 패턴을 모두 잡아냅니다.

**Scoring.** Stage 2와 Stage 3 결과를 3-Tier 모델로 합산합니다.

**Report.** 최종 평가 리포트를 생성하고, 대시보드를 업데이트하고, 알림을 보내고, Docker 리소스를 정리합니다.

## 채점 모델의 진화: 17번의 변경, 26번의 초기화

채점 모델은 사전에 설계된 것이 아닙니다. 36일에 걸쳐 17번의 모델 변경과 26번의 결과 전체 초기화를 거치며 발견된 것입니다.

### pass/fail에서 래더 채점으로

처음에는 TC마다 이진 pass/fail로 시작했습니다. 바로 한계에 부딪혔습니다. 두 지원자 모두 동시성 테스트를 "pass"했지만, 한 명은 매번 완벽하게 처리하고 다른 한 명은 들쭉날쭉합니다. 같은 pass인데 역량은 완전히 다릅니다.

그래서 **래더 정수 채점**으로 바꿨습니다: 각 TC에 5-6개의 이름 붙은 수준이 있고, 각 수준이 특정 점수에 매핑됩니다. 동시성 레이스 테스트(TC-A1)의 예:

| 수준 | 점수 | 기준 |
|------|------|------|
| 5 | 10 | 3회 모두 정확히 1명 성공 + 명확한 에러 응답 |
| 4 | 8 | 3회 모두 정확히 1명 성공 |
| 3 | 6 | 3회 중 2회 정확 |
| 2 | 4 | 1-2명이 일관되게 성공 (제어는 되지만 정확하지 않음) |
| 1 | 2 | 부분적 제어 (2-9명 성공) |
| 0 | 0 | 동시성 제어 없음 |

"거의 됐는데 가끔 실패"도 부분 점수를 받습니다. 이진 채점이 파괴하는 스펙트럼을 포착합니다.

### 단순 합산에서 3-Tier로

래더 채점으로 TC별 디테일은 살렸지만 더 큰 문제가 드러났습니다: **빌드가 실패하면 기능 테스트 전체가 0점인데, 코드 품질은 탁월한 지원자가 있었습니다.** 사려 깊은 아키텍처, 잘 구성된 프롬프트, 명확한 요구사항 도출. 그런데 Gradle 버전이 안 맞아서 0점. 빈 프로젝트를 제출한 지원자와 같은 통에 넣는 건 공정하지 않습니다.

이 문제가 평가의 뼈대가 된 분리를 강제했습니다:

```
Base  = Tier 1 (Make it Work, 6점) + Tier 2 (Basic Features, 94점) = 100점
Depth = Tier 3 (Deep Thought, ~120점)
Total = Base + Depth ≈ 220점
```

**Base**는 Stage 3에서 나옵니다. Docker 기능 테스트. 코드가 *동작하는가?*

**Depth**는 Stage 2에서 나옵니다. AI 코드 리뷰. 지원자가 *이해하고 있는가?*

핵심: 이 둘은 독립적으로 채점됩니다. 빌드 실패(Base = 0)해도 Depth는 영향받지 않습니다. Docker가 안 되지만 코드 설계가 뛰어난 지원자도 Depth 점수는 받고, 면접 기회를 얻을 수 있습니다.

### 보상 공식

순수한 분리는 또 다른 문제를 만들었습니다: 예외적인 깊이(100/120)지만 보통 수준의 기능(70/100)인 지원자가, 높은 기능(90)이지만 얕은 깊이(50)인 지원자보다 순위가 낮았습니다. 직관적으로는 첫 번째 지원자, 깊은 이해 + 약간 부족한 실행이 더 유망해 보이는데 말입니다.

여러 차례 반복 끝에 보상 공식을 만들었습니다:

```
effective_base = base + max(0, depth - depth_requirement) / 2
```

`/ 2`가 핵심입니다. Depth 초과분이 2:1 비율로 Base에 보상됩니다. 탁월한 사고력이 기능 부족을 부분적으로 만회할 수 있지만, 1:1은 과합니다. 동작하는 코드를 배포해야 한다는 원칙은 유지됩니다. 그리고 Base가 일정 수준 미만이면 보상이 적용되지 않는 하한 메커니즘도 추가했습니다.

### 7단계 랭크 시스템

채점 모델은 총점을 산출하지만, 숫자 하나로는 부족합니다. 150점인 두 지원자가 완전히 다를 수 있습니다: 한 명은 Base 90 + Depth 60이고, 다른 한 명은 Base 60 + Depth 90입니다. 그래서 점수의 크기가 아닌 형태를 포착하는 랭크 시스템을 도입했습니다:

| 랭크 | Base 요건 | Depth 요건 | 시그널 |
|------|----------|-----------|--------|
| **Ace** | ≥ 82 | ≥ 80 | 즉시 채용 추천 |
| **Craftsman** | ≥ 82 | ≥ 45 | 채용 추천 |
| **Hustler** | ≥ 82 | < 45 | 기능은 완벽, 이해 확인 필요 |
| **Contender** | ≥ 64 | — | 면접 추천 |
| **Thinker** | 빌드 실패 | ≥ 75 | 뛰어난 사고, 빌드만 삐끗 |
| **Rookie** | ≥ 44 | — | 추가 검증 필요 |
| **Incomplete** | 미달 | — | 기준 미달 |

**Hustler**가 가장 흥미로운 랭크입니다. 코드가 완벽하게 동작합니다. 모든 테스트 통과, 동시성 처리, 엣지 케이스 커버. 하지만 Depth 점수가 낮습니다. 프롬프트는 얕은 관여를 보이고, 설계 문서는 빈약하고, git 이력은 복붙 후 넘어가기 패턴입니다. 기능적 결과물은 훌륭하지만 이해의 증거가 약합니다. 이것이 AI 과의존 신호입니다. 이 시리즈 Part 3에서 이들을 면접했을 때 무슨 일이 있었는지 다루겠습니다.

**Thinker**는 가장 안타까운 랭크입니다. 이 랭크를 받은 지원자가 한 명 있었습니다: 환경 미스매치로 Docker 빌드가 실패해서 Base 점수가 0이었지만, 코드 설계, 요구사항 도출, 프롬프트 품질이 상위권이었습니다. 순수 기능 평가라면 즉시 탈락이었을 것입니다. 우리 시스템은 말했습니다: 이 사람은 사고력이 뛰어나지만 DevOps에서 삐끗한 것뿐이다. 면접은 볼 가치가 있다.

### 실제 분포

| 랭크 | 인원 | 비율 |
|------|------|------|
| Ace | 64 | 17.5% |
| Craftsman | 154 | 42.1% |
| Hustler | 18 | 4.9% |
| Contender | 54 | 14.8% |
| Thinker | 1 | 0.3% |
| Rookie | 26 | 7.1% |
| Incomplete | 49 | 13.4% |

채용 추천 (Ace + Craftsman): **218명 (59.6%)**. 면접 추천 (Hustler + Contender + Thinker): **73명 (19.9%)**. 기준 미달: **75명 (20.5%)**.

59.6%의 채용 추천율은 예상보다 높았습니다. 지원자 풀의 수준이 높은 건지, 아니면 AI 활용 제출물에 대한 Depth 기준이 너무 관대한 건지. 보정했습니다. 캘리브레이션에 끝은 없습니다.

## 머신을 신뢰할 수 있는가

AI가 AI 활용 코드를 평가하면 신뢰 문제가 생깁니다. AI 채점자가 점수를 환각하고 있지는 않은지? 평가 순서에 편향되지는 않았는지? 같은 제출물을 두 번 채점하면 같은 점수가 나오는지?

답: 단일 레이어를 신뢰하지 않습니다. 세 개를 쌓습니다.

    B --> C["Layer 3<br/>수동 보정<br/>(Delta ±10)"]
    C --> D["최종 점수"]

    B -->|"overscored /<br/>underscored 플래그"| C

    style B fill:#7c3aed,stroke:#333,color:#fff
    style C fill:#16a34a,stroke:#333,color:#fff
{{< /mermaid >}}

**Layer 1 — AI 평가.** 1차 채점. Stage 2가 코드를 읽고 품질을 채점합니다. Stage 3가 Docker 테스트를 돌리고 기능을 채점합니다. 모든 점수에 근거가 필요합니다.

**Layer 2 — AI 정당화.** 별도의 에이전트가 지원자의 코드를 다시 읽으며 Layer 1 점수를 교차 검증합니다. Stage 2에서 "에러 처리: 2점 — @ControllerAdvice 사용"이라고 했는데, 정당화 에이전트가 코드에서 `@ControllerAdvice`를 찾지 못하면 `overscored` 플래그. Stage 3에서 빌드 실패로 0점을 줬는데 코드 경로를 추적(Controller → Service → Repository)해보면 로직이 사실은 정확하면 `underscored` 플래그.

**Layer 3 — 수동 보정.** 정당화 레이어가 불일치를 표시하면, 사람이 검토하고 항목당 -10~+10점의 보정을 적용합니다. 감사 추적을 위해 보정 사유가 구조화된 형태로 기록됩니다.

캘리브레이션 데이터에서 드러난 핵심 인사이트: AI는 특정 카테고리를 일관되게 과대 채점했습니다. 특히 "추가 구현" 항목(캐싱, 모니터링 같은 비즈니스 확장)에서 AI가 존재하지만 잘 통합되지 않은 기능에 후한 점수를 줬습니다. 이런 체계적 편향을 파악한 뒤 채점 지침에 캘리브레이션 힌트를 추가해서 이후 실행의 변동을 줄였습니다.

## 머신을 운영하다

숫자가 운영의 이야기를 합니다:

| 지표 | 값 |
|------|-----|
| 총 커밋 | 1,952 |
| 개발 기간 | 36일 |
| 평가 커밋 | 1,162 (59.5%) |
| 평가한 지원자 | 366명 |
| 채점 모델 변경 | 17회 |
| 결과 초기화 | 26회 |
| 자동화 워크플로우 | 20+ |
| JSON 스키마 | 7개 |
| 파이프라인 지침 파일 | 26개 (11 skills + 15 commands) |
| 기여자 | 3명 |

가장 의미 있는 숫자: **시스템을 만드는 커밋(feat/fix/refactor)이 14.5%, 시스템으로 일하는 커밋(evaluation)이 59.5%.** 만드는 데 1의 노력이 들었다면 돌리는 데 4의 노력이 들었습니다.

5대의 머신이 병렬로 평가를 수행했고, 각 머신은 컨텍스트 오염(AI가 지원자 N을 평가할 때 1~N-1의 리뷰 내용에 영향받는 것)을 방지하기 위해 순차 처리했습니다. 지원자마다 격리된 에이전트 세션을 부여했습니다. 토큰 한도 때문에 10개 계정을 돌려 쓰며 사용량이 임계치에 가까워지면 교체했습니다.

n8n 기반 자동화 허브가 AI 평가 너머의 모든 것을 조율했습니다: 지원자 명단 관리, 중복 평가 방지를 위한 분산 잠금, 진행 대시보드, 결과 집계, 알림. 이것이 "빙산의 수면 아래" — AI 채점이 보이는 부분이었지만, 그 아래의 행정 자동화가 적어도 그만큼 컸습니다.

원천 데이터는 의외로 평범했습니다: Google Sheets. HR이 지원자 명단을 시트로 관리하면, 자동화 파이프라인이 DB에 동기화하고, GitHub 초대를 발송하고, 제출 URL을 수집하고, 평가 상태를 추적했습니다. 프로세스에 참여하는 비개발자들은 자기 스프레드시트를 벗어날 일이 없었습니다.

## 다음은

파이프라인은 *누구를* 면접할지 알려주고 정량화된 신호를 제공합니다. 하지만 점수와 랭크만으로는 면접실에 들어갈 수 없습니다. 각 사람에게 *무엇을 물을지* 알아야 하고, 그 질문은 그들의 코드, 설계 결정, 약점에 특화되어야 합니다.

여기서 머신의 Part B가 시작됩니다: 각 지원자의 제출물을 읽고 맞춤형 면접 가이드를 생성하는 AI 시스템. `file:line` 증거에 연결된 질문, 수준별 예상 답변, 소크라테스식 후속 질문까지. 머신의 판단과 사람의 대화를 잇는 다리입니다.

[Part 2-2, "Under the Hood"](/posts/2026-02-24-ai-native-hiring-under-the-hood.ko/)에서 이명훈이 실제 산출물 안으로 들어갑니다. 채점 루브릭, TC 래더, 366개의 서로 다른 API 설계에 대한 엔드포인트 탐지, 그리고 면접 가이드 생성 시스템. 이 글이 아키텍처라면 그 글은 구현입니다.

그리고 Part 3, "The Human"에서는 AI가 만든 면접 가이드를 들고 면접관이 지원자 앞에 앉았을 때 무슨 일이 있었는지를 다루겠습니다. AI를 직접 채용하는 게 아닌 이상, 사람을 최종 평가하는 건 사람의 몫이니까요.
