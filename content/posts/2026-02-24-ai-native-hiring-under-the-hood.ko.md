# Part A: 평가 파이프라인

## 채점 루브릭: 깊이의 8가지 차원

Stage 2(AI가 지원자의 코드를 읽는 단계)는 8개 영역에 걸쳐 총 약 120점을 채점합니다. 임의의 카테고리가 아닙니다. Part 1의 철학에 대응합니다: AI 시대에는 *AI에게 무엇을 시켰는가*가 *AI가 무엇을 만들었는가*만큼 중요합니다.

| 영역 | 점수 | 평가 대상 |
|------|------|----------|
| **프롬프트** | 18 | AI 협업에서의 사고 깊이 — 근본 원인 탐구, 트레이드오프 인식, 엣지 케이스 발굴 |
| **에이전트 지침** | 17 | AI에게 프로젝트 맥락을 얼마나 잘 전달했는가 (AGENTS.md, CLAUDE.md 등) |
| **요구사항 도출** | 18 | 의도적으로 모호한 문제를 자기 언어로 재구조화했는가? 동시성 분석, 락 설계 논거 |
| **데이터 설계** | 17 | 스키마 정규화, 현실적 시드 데이터 품질, 배치 삽입 전략, DB 제약조건과 인덱싱 |
| **코드 품질** | 19 | 아키텍처 레이어링, 에러 처리, 응답 일관성, 의존성 관리, 트랜잭션 처리 |
| **테스트 품질** | 10 | 단위·통합·E2E·동시성 테스트 커버리지 |
| **Git 이력** | 5 | 의미 있는 커밋 단위, 서술적 메시지 |
| **추가 구현** | 10 | 스펙 이상의 작업: 캐싱, 모니터링, API 문서화, 성능 최적화 |

처음 두 영역인 **프롬프트**와 **에이전트 지침**은 AI 네이티브 평가만의 고유한 항목입니다. 기존 코드 리뷰는 엔지니어가 도구와 어떻게 소통했는지 보지 않습니다. 하지만 그 도구가 AI 에이전트일 때, 소통의 품질은 엔지니어링의 일부입니다.

### 감이 아니라 근거

모든 점수에는 근거가 필요합니다. AI 평가자가 "에러 처리 잘됨 — 2점"이라고 할 수 없습니다. 반드시 이런 식이어야 합니다:

> `src/handler/GlobalExceptionHandler.java:15` — `@ControllerAdvice` 기반 전역 예외 처리기, `ErrorCode.java:5-40`에 도메인별 에러 코드 매핑.

이 근거 요구사항은 두 가지 목적을 섬깁니다. 첫째, AI가 그럴듯한 평가를 생성하는 대신 실제 코드에 점수를 근거하도록 강제합니다. 둘째, 정당화 레이어(Part 2-1의 Layer 2)가 교차 검증할 수 있는 감사 추적을 만듭니다.

루브릭은 각 채점 항목에 대해 근거가 어떤 모습이어야 하는지 정의합니다. "프롬프트" 영역에서는 특정 신호를 체크합니다:

```yaml
# 채점 루브릭 예시
prompts:
  insight_depth:
    keywords: ["왜", "트레이드오프", "예외", "만약", "edge case"]
    check: "후보자가 HOW가 아니라 WHY를 탐구하는가?"
    evidence_type: quote  # 프롬프트 파일에서 직접 인용
  ambiguity_exploration:
    check: "문제 진술의 빈틈을 식별했는가?"
    evidence_type: file_line  # 특정 프롬프트 파일과 라인 참조
```

개발 초기에 발견한 사실: 이 체크리스트 방식 없이는 같은 지원자에 대한 AI 점수가 세션마다 ±6-11점 변동했습니다. 증거 체크리스트를 도입한 뒤 변동이 ±3으로 줄었습니다.

## 테스트 케이스 설계: 래더 정수 채점

Stage 3은 8개 카테고리에 걸쳐 25개 TC를 실행합니다. 모든 TC는 **래더 정수 채점**을 사용합니다. pass/fail이 아니라 달성 수준의 명명된 스펙트럼입니다.

실제 TC 정의의 모습입니다:

### TC-B1: 중복 수강 방지 (5점)

> 같은 학생이 같은 강좌에 5번 연속 수강신청 시도.

| 수준 | 점수 | 의미 |
|------|------|------|
| 0 | 0 | 중복 체크 없음 — 5번 모두 성공 |
| 1 | 1 | 비일관적 — 중복이 때로는 차단, 때로는 통과 |
| 2 | 2 | 일관된 4xx 에러로 중복 차단 |
| 3 | 3 | 의미 있는 에러 메시지를 포함한 4xx (범용 500이 아님) |
| 4 | 4 | 409 Conflict + 멱등 처리 |
| 5 | 5 | 409 + 에러 응답에 원래 수강신청 참조 포함 |

Level 5는 드뭅니다. 대부분의 프로덕션 API도 충돌 시 원본 리소스 참조를 반환하지 않습니다. 하지만 이것까지 하는 지원자는 최소한을 넘어서는 API 설계 감각을 보여줍니다.

### TC-A1: 동시성 레이스 — 잔여 1석 (10점)

> 강좌 수강신청을 채워서 정확히 1석만 남긴다. 100개 동시 요청 전송. 통계적 신뢰도를 위해 3회 반복.

| 수준 | 점수 | 의미 |
|------|------|------|
| 0 | 0 | 동시성 제어 없음 — 다수 성공 |
| 1 | 2 | 부분적 제어 (2-9명 일관되게 성공) |
| 2 | 4 | 1-2명 일관 성공 (제어는 되지만 정확하지 않음) |
| 3 | 6 | 3회 중 2회 정확히 1명 성공 |
| 4 | 8 | 3회 모두 정확히 1명 성공 |
| 5 | 10 | 3회 모두 정확 + 실패 시도에 명확한 에러 응답 |

3회 반복이 중요합니다. 동시성 버그는 확률적입니다. 1회만 돌리면 운으로 통과할 수 있습니다. 3회가 비결정적 실패를 드러냅니다.

동시성 카테고리만 3개 TC(TC-A1~A3)에 걸쳐 22점으로, 가장 큰 비중입니다. Part 1의 철학을 반영합니다: 동시성 요구사항이 의도적으로 모호한 문제의 가장 깊은 층이었으니까요.

### 카테고리별 배점 분포

```

비즈니스 규칙   ██████████████████  18점   (학점 제한, 충돌)
동시성          ██████████████████████  22점   (어려운 부분)
성능            ████████░░  10점   (응답 시간, 처리량)
데이터 품질     ████████████  12점   (시드 데이터 현실성)

엣지 케이스     ████████  8점    (경계 조건)

## 엔드포인트 탐지 문제

예상 못한 문제: **366명의 지원자 = 366가지 다른 API 설계.**

같은 "수강신청" 기능이 이럴 수 있습니다:

```
지원자 A: POST /enrollments           {"studentId": 1, "courseId": 5}
지원자 B: POST /api/v1/enrollments     {"student_id": 1, "course_id": 5}
지원자 C: POST /courses/5/enroll       (X-Student-Id: 1 헤더)
지원자 D: POST /registrations          {"studentId": 1, "courseId": 5}
```

TC에 엔드포인트를 하드코딩할 수 없습니다. 그래서 3단계 엔드포인트 탐지 시스템을 만들었습니다:

**1단계 — 정적 분석.** 소스코드에서 프레임워크별 라우팅 패턴을 grep합니다:

```
Spring Boot:  @PostMapping, @GetMapping, @RequestMapping
Express:      app.post('/...'), router.get('/...')
FastAPI:      @app.post('/...'), APIRouter(prefix='/...')
NestJS:       @Controller('...'), @Post()
```

클래스 레벨 prefix와 메서드 레벨 path를 결합해서 전체 경로를 조합합니다.

**2단계 — 런타임 검증.** Docker 기동 후, 탐지된 모든 엔드포인트에 프로브 요청을 보냅니다. 코드에 선언은 되어 있지만 실제로 응답하지 않는 엔드포인트(미완성 구현, 비활성 라우트)를 걸러냅니다.

**3단계 — 기능 매핑.** 검증된 엔드포인트를 TC 기능에 매핑합니다:

```
수강신청: /enrollments 또는 /registrations 또는 /courses/{id}/enroll → 응답하는 것
수강취소: /enrollments/{id} 또는 /enrollments/{id}/cancel → 응답하는 것
시간표:   /students/{id}/schedule 또는 /students/{id}/timetable → 응답하는 것
```

비동기 API도 자동 감지했습니다. 일부 지원자는 수강신청을 비동기로 구현했습니다. POST가 `jobId`나 `PENDING` 상태를 반환하고, 결과를 폴링합니다. 첫 수강신청 테스트에서 이 패턴이 감지되면, 이후 모든 TC가 폴링 모드로 전환됩니다.

## 빌드 구제와 Graceful Degradation

제출물의 약 15%가 빌드에 실패했습니다. 하지만 "빌드 실패"는 하나가 아닙니다. 스펙트럼입니다:

| 실패 유형 | 부분 점수 | 예시 |
|-----------|----------|------|
| **환경/설정 문제** | 28점 | Gradle 버전 미스매치, npm 의존성 충돌, DB 연결 문자열 |
| **컴파일 에러** | 14점 | 문법 오류, import 누락, 타입 불일치 |
| **핵심 부재** | 0점 | 빈 프로젝트, 컨트롤러 없음, 소스코드 없음 |

분류는 언어 생태계별 패턴 매칭을 사용합니다:

```yaml
# evaluation.yaml에서
environment_issue:
  java: ["Could not resolve all dependencies", "incompatible version"]
  node: ["npm ERR!", "Cannot find module", "ECONNREFUSED"]
  python: ["ModuleNotFoundError", "ConnectionRefusedError"]

compile_error:
  java: ["cannot find symbol", "incompatible types"]
  node: ["SyntaxError", "TypeError"]
  python: ["SyntaxError", "IndentationError"]
```

"npm 버전 미스매치"와 "빈 프로젝트"는 다른 이야기입니다. 전자는 버전 하나만 맞추면 동작할 가능성이 높습니다. 후자는 평가할 것이 없습니다.

**빌드 교정**도 도입했습니다. 지원자의 소스코드는 건드리지 않고, 인프라만 수정하는 시도입니다. 정책은 Depth 점수에 따라 차등 적용:

- Depth ≥ 75: 최대 5회 교정 시도 (DB 버전, 베이스 이미지, 환경 변수, wrapper 권한, 대체 Dockerfile)
- Depth ≥ 60: 최대 3회
- Depth < 60: 1회 기본 시도만

논리: AI 코드 리뷰에서 이 지원자가 뭘 하는지 이해한다고 판단되면(높은 Depth), 빌드를 살리기 위해 더 노력할 가치가 있습니다. 이해가 얕다면 빌드 실패가 단순 DevOps 문제가 아닐 가능성이 높습니다.

교정된 빌드는 리포트에 투명하게 표시됩니다. 그리고 교정으로 살린 빌드는 TC-01(Docker Build)에서 Level 1로 캡이 걸립니다. 도움받은 빌드에 만점을 주지 않습니다.

## 마크다운이 곧 파이프라인

전체 평가 파이프라인이 마크다운 지침 파일로 정의되어 있습니다. 컴파일된 평가 애플리케이션은 없습니다. AI 에이전트가 이 문서를 읽고 실행합니다.

평가 명령의 작동 방식을 단순화하면:

```
evaluate-candidate (오케스트레이터)
│
├── 로드: init/SKILL.md
│   └── Git clone, 마감 체크, checkout
│
├── 로드: stage0/SKILL.md
│   └── 보안 스캔 (쉘 스크립트 실행)
│
├── 로드: stage1/SKILL.md
│   └── 형식 검증
│
├── 로드: stage2/SKILL.md
│   └── 전체 코드 읽기 → 8개 영역 채점 → JSON 출력
│
├── 로드: stage3/SKILL.md
│   └── 언어 탐지 → Docker 빌드 → 엔드포인트 탐지
│   └── 25개 TC 실행 → 래더 채점 → JSON 출력
│
├── 로드: scoring/SKILL.md
│   └── 3-Tier 산출 → 랭크 결정
│
└── 로드: report/SKILL.md
    └── 리포트 생성 → 대시보드 업데이트 → 알림 → 정리
```

배치 처리에는 상위 지침 파일이 루프를 오케스트레이션합니다:

```
FOR candidate_id IN 미평가자:
    IF 결과 이미 존재: SKIP
    TRY:
        격리된 에이전트 세션 시작
        실행: evaluate-candidate {candidate_id}
        기록: 성공
    CATCH:
        기록: 에러, 다음으로 계속
```

이건 Python도 쉘도 아닙니다. AI 에이전트가 읽고 해석하는 의사코드입니다. 제어 흐름은 명시적(`FOR`, `IF`, `TRY/CATCH`)이지만, 문법은 유연합니다. 중요한 건 문법이 아니라 *의도*입니다.

순차 vs 병렬 실행은 성능이 아닌 안전성 기준으로 결정됩니다:

| 작업 | 동시성 | 이유 |
|------|--------|------|
| AI 코드 리뷰 | 순차 (1) | 컨텍스트 격리 필수 — 채점 편향 방지 |
| Docker 테스트 | 순차 (1) | 컨테이너 간 포트·메모리 경합 |
| 점수 산출 | 병렬 (5) | JSON 읽기/쓰기만 — 충돌 없음 |
| 점수 정당화 | 병렬 (3) | AI 집약적이지만 지원자별 완전 독립 |

## JSON 스키마라는 계약

AI 에이전트는 창의적입니다. 때로는 너무 창의적입니다. 제약 없이 두면 평가 에이전트가 이런 걸 출력할 수 있습니다:

```json
{
  "score": 85,
  "rank": "Ace",
  "memo": "이 후보자 정말 잘함",
  "vibes": "excellent"
}
```

도움이 되긴 하지만, 후처리에는 쓸 수 없습니다.

7개의 JSON 스키마가 모든 단계 출력에 구조적 계약을 강제합니다. 에이전트가 JSON을 생성하면, 시스템이 스키마로 검증하고, 실패하면 에러 메시지를 에이전트에게 돌려보내 자기 수정하게 합니다. 최대 5회 반복.

```
에이전트가 JSON 생성
  → 스키마 검증
  → 실패: "score 필드가 최대 범위 초과; 'evidence' 배열 누락"
  → 에이전트가 에러를 읽고 자기 수정
  → 재검증
  → 통과 (또는 재실패, 최대 5회)
```

엄격 모드는 추가 필드를 허용하지 않습니다. 스키마에 `score`와 `rank`가 정의되어 있으면, 에이전트가 `memo`나 `vibes`를 몰래 넣을 수 없습니다. 사소해 보이지만, 366명 규모에서는 구조적 불일치 하나하나가 통계, CSV 내보내기, 대시보드 시각화의 다운스트림 버그가 됩니다.

# Part B: AI 맞춤 면접 가이드

평가 파이프라인이 366명을 채점하고 면접 대상을 선별했습니다. 108명이 최종 라운드에 진출했습니다. 각각에게 맞춤형 면접 가이드가 필요했습니다. 범용 기술 질문이 아니라, *이 사람의 코드*, *이 사람의 약점*, *이 사람의 강점*에 특화된 질문이요.

## Deep Insight: 지원자별 맞춤 면접 가이드

Deep Insight 시스템은 파이프라인이 한 지원자에 대해 생산한 모든 것을 읽습니다. 소스코드 저장소, Stage 2 품질 점수, Stage 3 기능 결과, 1차 온라인 코딩 테스트 답안까지. 그리고 맞춤형 면접 가이드를 생성합니다.

생성된 가이드의 구성:

**1. 지원자 프로필.** 랭크, 점수, 코호트 내 백분위 위치. 전체 366명 중, 그리고 면접 풀 108명 중 어디에 서 있는지.

**2. Part A — 기술 검증 질문 (3-5개).** 각 질문이 구체적 코드 증거에 연결됩니다:

> **질문 2: 이중 락 전략과 데드락 인식**
>
> *코드 증거:* `EnrollmentService.java:30-59` — 지원자가 두 개의 `ReentrantLock` 인스턴스(`courseLock`, `studentLock`)로 동시 수강신청을 직렬화.
>
> ```java
> // 지원자의 실제 제출 코드에서
> private final Map<Long, ReentrantLock> courseLocks = new ConcurrentHashMap<>();
> private final Map<Long, ReentrantLock> studentLocks = new ConcurrentHashMap<>();
> ```
>
> *질문:* "두 개의 별도 락 맵을 사용하고 계시네요. 사고 과정을 설명해주세요 — 왜 락을 하나가 아니라 둘로 나누셨나요? 두 학생이 서로의 강좌에 동시에 등록하려 하면 어떤 일이 생기나요?"
>
> *기대 답변 (5점):* 강좌 레벨 락이 정원을, 학생 레벨 락이 학생별 제약(학점 제한, 시간 충돌)을 보호한다고 설명. 데드락 방지를 위한 락 순서 전략을 기술.
>
> *기대 답변 (3점):* 두 락의 범위를 이해하지만 데드락 순서는 고려하지 않음.
>
> *기대 답변 (1점):* 코드가 하는 일은 설명할 수 있지만 왜 락이 두 개 필요한지 설명 못 함.
>
> *후속 질문:* "이 서비스를 여러 서버 인스턴스에 배포한다면, 이 락 전략이 여전히 동작할까요?"

**3. 부정행위 검증.** 1차 온라인 코딩 테스트의 질문을 대면에서 다시 물어봅니다. 이전 제출물을 스스로 설명 못 하면 플래그입니다.

**4. Part B — 가치관 질문.** MUSINSA WAY 행동 면접 질문, 지원자 프로필에 맞게 조정. 이것마저도 코드 증거에 연결될 수 있습니다. 예를 들어 "학습 민첩성"을 물으면서 지원자의 프롬프트 이력(과제 중 락 개념을 처음부터 AI를 통해 학습했다는 기록)을 참조하는 식입니다.

질문 생성의 설계 원칙: **약점을 직접 언급하지 않는다.** 지원자의 코드에 시간 충돌 감지 버그가 있다면(예: 시간 겹침 대신 `equals()` 비교), "충돌 체크가 잘못됐습니다"라고 하지 않습니다. 소크라테스식입니다: "월요일 09:00-10:30 강좌와 월요일 10:00-11:30 강좌가 있으면, 시스템이 겹침을 감지할까요? 코드 경로를 따라가 볼까요?"

면접관은 기대 답변을 알고 있습니다. 지원자가 스스로 빈틈을 발견합니다. 아니면 이미 이해하고 있음을 드러냅니다.

## S2 × S3 매트릭스: 점수 프로필별 면접 전략

모든 지원자에게 같은 면접이 필요한 건 아닙니다. Stage 2 (Depth) × Stage 3 (Base) 격자에서 어디에 위치하느냐에 따라 면접 전략이 달라집니다:

{{< mermaid title="점수 프로필별 면접 전략" >}}
quadrantChart
    title S2 (Depth) × S3 (Base) 면접 전략
    x-axis "낮은 Base (기능)" --> "높은 Base (기능)"
    y-axis "낮은 Depth (이해)" --> "높은 Depth (이해)"
    quadrant-1 "Ace / Craftsman: 한계를 밀어보기"
    quadrant-2 "Thinker: 디버깅, DevOps"
    quadrant-3 "Incomplete: 기본 확인"
    quadrant-4 "Hustler: 이해도 검증"
{{< /mermaid >}}

- **높은 Base + 높은 Depth (Ace/Craftsman):** 아키텍처의 경계를 밀어봅니다. 분산 시스템, 확장성 트레이드오프, 시간이 더 있었다면 바꿨을 것.
- **높은 Base + 낮은 Depth (Hustler):** AI 의존도 체크. "이 함수를 한 줄 한 줄 설명해 보세요." "왜 이 락을 선택하셨나요?" 기능은 완벽 + 이해가 얕음 = AI 생성에 대한 과의존 가능성.
- **낮은 Base + 높은 Depth (Thinker):** 디버깅과 환경 역량에 집중. 사고력은 있는데 실행이 삐끗했습니다. 자기 빌드 실패를 진단할 수 있는가? 힌트를 주면 얼마나 빨리 복구하는가?
- **낮은 Base + 낮은 Depth:** 기본 확인. 성장 가능성이 있는가? 이 경험에서 무엇을 배웠는가?

108명 중 16명이 "특별 관리" 대상으로 표시되었습니다. S2/S3 프로필이 충분히 이례적이어서 면접관 사전 준비가 추가로 필요한 경우입니다.

## 행동 앵커와 힌트 복구 규칙

면접관은 주니어 지원자에 맞게 보정된 행동 앵커가 있는 5점 척도로 채점합니다:

| 점수 | 수준 | 어떤 모습인가 |
|------|------|-------------|
| 5 | 탁월 | 면접관이 묻지 않은 개념을 스스로 설명. 더 큰 시스템과의 연결. |
| 4 | 우수 | 정확하게 답하고, 트레이드오프를 이해하고, 가상 시나리오로 확장 가능. |
| 3 | 보통 | 핵심 이해는 탄탄하지만 직접 구현한 것 이상으로 나아가지 못함. |
| 2 | 미흡 | 부분적 이해. 코드가 *무엇을* 하는지는 설명하지만 *왜* 그런지는 못함. |
| 1 | 부족 | 자신의 구현을 설명하지 못함. |

**힌트 복구 규칙**이 뉘앙스를 더합니다. 면접은 시험이 아닙니다. 지원자가 처음에 놓쳤지만 힌트 후 복구하면:

- **힌트 없이 정답:** 만점
- **힌트 1회 → 올바르게 확장:** −0.5점
- **힌트 2회 이상 → 결국 정답:** 한 수준 하락
- **힌트가 도움이 안 됨:** 현재 수준 유지

긴장해서 더듬거리지만 실력 있는 지원자를 부당하게 깎지 않기 위한 장치입니다. 면접은 대화이지, 함정이 아닙니다.

Part A는 세 가지 차원을 다룹니다: 아키텍처 이해(시스템 구조를 설명할 수 있는가?), 기술 깊이(동시성, 엣지 케이스, 트레이드오프를 논할 수 있는가?), 부정행위 검증(이 코드를 본인이 정말 작성했는가?).

Part B는 SBI 기법(Situation-Behavior-Impact)으로 MUSINSA WAY 가치를 평가합니다. 주니어 맞춤 핵심 조정: "경험의 규모"가 아니라 "경험의 밀도"를 봅니다. 3명 프로젝트에서 명확한 오너십을 보인 주니어가, 30명 이니셔티브를 이끈 시니어와 같은 행동 신호를 보여줍니다. 스케일은 다르지만 마커는 같습니다.

### 추천 매트릭스

```
강력 추천:   Part A 평균 ≥ 4.0 AND Part B 핵심 평균 ≥ 4.0
추천:        Part A 평균 ≥ 3.5 AND Part B 핵심 평균 ≥ 3.5
보류:        어느 한쪽 평균 2.5-3.5
비추천:      어느 한쪽 평균 < 2.5
```

## 스코어카드 파이프라인

면접관이 마크다운 스코어카드를 채웁니다. 체크리스트, 5점 척도, 각 차원의 증거 블록이 있는 구조화된 문서입니다. 완성된 스코어카드의 간략한 예:

```markdown
## A-1. 아키텍처 이해 (1-5)

체크리스트:
- [x] 전체 시스템 아키텍처를 말로 설명 가능
- [x] 각 레이어(Controller/Service/Repository)의 역할을 이해
- [ ] 이 아키텍처를 선택한 이유를 대안과 비교해 논할 수 있음
- [x] 자기 설계의 개선점을 스스로 식별

점수: 3.5

증거:
> "이중 락 구조와 에러 처리 체계를 설명할 수 있었으나,
> 다른 아키텍처 대안에 대한 비교는 깊지 않았음."
```

이 스코어카드들은 자동 파싱됩니다: 마크다운 → JSON → CSV. 하지만 흥미로운 건 파싱 *이후*입니다:

**캘리브레이션 분석.** 5개 배치의 면접관이 108명을 평가하면 면접관 편향이 불가피합니다. 면접 점수 대 사전 점수(Stage 2 + Stage 3)에 대해 OLS 회귀를 돌려 면접관별 체계적 관대함·엄격함을 탐지합니다. 어떤 면접관은 기대선 대비 평균 +0.19, 다른 면접관은 -0.15. 이 효과를 계산해서 채용 위원회에 투명하게 제공합니다.

**온도 분석.** 어조-점수 일관성을 별도로 체크합니다. 스코어카드의 서술 증거가 수치 점수와 맞는가? 면접관이 열정적인 메모("탁월한 이해도, 깊은 사고력")를 적었는데 3/5점이거나, 비판적 메모를 적었는데 4/5점이면, 시스템이 불일치를 플래그합니다.

**3단계 디브리프 스택.** 최종 채용 위원회는 세 레이어를 봅니다:

1. **원점수** — 면접관이 보고한 그대로
2. **온도 보정** — 어조-점수 불일치 교정
3. **캘리브레이션 보정** — 면접관 편향 교정

어떤 레이어도 면접관의 판단을 덮어쓰지 않습니다. 하지만 조합하면 원점수만으로는 볼 수 없는 더 완전한 그림을 채용 위원회에 제공합니다.

## 마무리

Part 2-1과 2-2에 걸쳐 조립된 시스템은 세 가지 맞물리는 구성 요소를 가집니다: **평가 파이프라인** (AI가 코드를 읽고, 머신이 코드를 돌림), **채점 모델** (래더 TC가 있는 3-Tier), **면접 준비** (코드 증거 기반 지원자별 AI 맞춤 가이드).

이 시스템이 366명을 처리하고, 108명의 면접 가이드를 생성하고, 5개 배치의 면접관을 지원했습니다. 매 단계마다 캘리브레이션과 품질 관리가 함께.

하지만 머신의 출력은 결국 사람의 결정을 위한 입력입니다. Part 3, "The Human"에서는 그 결정의 반대편에서 무슨 일이 있었는지 다루겠습니다. AI가 만든 면접 가이드를 들고 지원자 앞에 앉은 면접관들이, 어떤 머신도 대답할 수 없는 질문에 답해야 했던 이야기: *이 사람과 함께 만들고 싶은가?*

AI를 직접 채용하는 게 아닌 이상, 이 질문은 사람의 몫입니다.
